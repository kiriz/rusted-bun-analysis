Executive Summary

TL;DR

  • The claim. Anthropic's Claude Code rewrote Bun's entire Zig codebase in Rust — over a million lines — and the PR was merged into oven-sh/bun on May 14, 2026.
  • The commits are real. They were not rebased, squashed, or fabricated. 99.2% of commits have an author timestamp that matches the committer timestamp within two seconds — the signature of code written and committed in a continuous live stream.
  • The approach was structured. Work moved through explicit phases labeled a → h, with multiple sub-agent branches — every one of them named claude/* — merging fixes back into the main port branch.
  • The engineering plan was expert-grade. Before writing a line of Rust, the agent wrote its own 175-line crate-dependency analyzer (crate-dag.ts), then design documents specifying cycle-breaking and dispatch strategies — the canonical "instrument → spec → decompose" playbook for monolith-to-workspace migrations.
  • The AI-vs-human boundary is visible in the raw git objects. Every commit encodes the author's timezone: 6,635 commits are +0000 (Claude Code's UTC automated environment) versus 38 commits are -0700 (Jarred Sumner's Pacific-timezone Mac). The split marks exactly where the human intervened.
  • The speed has a simple explanation. Commits land roughly every nine seconds because the agent writes and commits without compiling. Verification is asynchronous — pushed off to CI and to dedicated fix-up branches.
  • The hard questions remain open. Code quality, the 14,000+ unsafe blocks still in the tree, and whether a 1M-line change with no human line-by-line review can be meaningfully audited — none of that is settled by the commit history alone.
Background

The Claim

Bun's creator, Jarred Sumner, has been increasingly public about a shift in how the runtime is built: that AI now writes essentially all of the code. PR #30412 is the clearest expression of that claim to date — a complete reimplementation of Bun's Zig core in Rust, attributed end to end to Anthropic's Claude Code agent. Sumner's framing was blunt: the human role is direction and review, not authorship.

Coverage in The Register and elsewhere amplified the headline number — a million-plus lines of a memory-safe rewrite, landed in a window measured in days — and treated it as a milestone moment for autonomous coding agents. Anthropic, for its part, has demonstrated Claude Code running long-horizon engineering tasks with sub-agents, CI integration, and self-triage of failures: the exact pattern the PR's branch topology shows.

That is the story as told. The rest of this page is the story as the git history actually records it — no press release, no speculation, just what 6,755 commits reveal when you read every one of them.

Methodology

What We Found — and How

Everything below is derived from public GitHub data. The process was deliberately mechanical so that any claim here can be independently re-checked:

  • 01 Cloned the repo as a blobless clone — about 56 MB — enough to walk the full commit graph without pulling every file blob.
  • 02 Extracted all 6,755 commits via git log, capturing SHA, author, committer, both timestamps, message, and parent SHAs.
  • 03 Compared author vs. committer timestamps for every single commit — the definitive test for whether history was rebased or rewritten after the fact.
  • 04 Sampled raw git objects with git cat-file -p to confirm the commit objects are well-formed and not synthetic.
  • 05 Analyzed the parent chain to separate linear commits from merge commits, and mapped which branches merged into the PR branch and how often.
  • 06 Inspected diff sizes per inter-commit gap bucket — to see whether fast commits carry small diffs (write-only) or large diffs (something else).
  • 07 Extracted raw timezone offsets from every git commit object via git cat-file -p, separating the +0000 automated commits from the -0700 human commits to identify where Jarred intervened directly.

No speculation about intent. Where the data is ambiguous, this page says so explicitly. The analysis scripts live alongside this page in the repository.

This is the most revealing part of the history. The PR was not one agent typing in a straight line — it was a main porting branch with a fleet of specialized sub-agent branches feeding fixes back into it.

The most revealing finding is not the commit velocity — it is what the agent did before writing a single line of Rust.

Commit message: phase-b0: add crate DAG analyzer

Before touching a single source file, the agent wrote a 175-line TypeScript program that maps the entire codebase: 96 crates, their intended dependency tiers (T0 zero-dep primitives through T6 subsystems), and which imports create cycles. You cannot safely extract a monolith into a multi-crate Cargo workspace without knowing the dependency graph first. The agent built its own instrumentation — then three docs: commits specifying cycle-breaking and dispatch strategies — before writing any migration code at all.

The migration playbook — reconstructed from the commit history

1
Instrument

Write crate-dag.ts — compute the full dependency DAG, assign tiers, identify cycles before touching anything.

2
Spec

Write design docs (docs: Dispatch, docs: CYCLEBREAK.md, docs: Concurrency) — the cross-crate dispatch strategy and cycle-breaking spec, committed before any code moves.

3
Break cycles — DELETE pass

Remove 99 spurious back-edge imports across 67 files that would create cycles in the new workspace. Cycle-breaking before extraction is the hard prerequisite.

4
Move-out passes

Relocate verified-clean crates to their tiers in three passes: 36 crates, then 4 fixed crates, then a final 4. "36 crates" was independently confirmed: exactly 36 distinct src/ subdirectories in the diff.

5
Move-in pass

Pull 579 symbols into 33 target crates, consolidating the symbol graph after the structural moves.

6
Collapse tier-6

Fold bake, shell, test_runner, cli, and napi into runtime/ — the top-level crate boundary.

7
Scaffold the Cargo workspace

One commit, 151 files, +3,184 lines, zero deletions: 96 per-crate Cargo.toml manifests plus the root workspace manifest, plus 52 autogenerated lib.rs files. "96 crates" confirmed exactly — 96 member manifests.

8
Prune back-edge deps

Remove back-edge dependencies from the generated manifests to enforce workspace acyclicity — the Cargo resolver requires a DAG.

9
Compile bottom-up — one crate per commit

Start from the lowest-tier crates and compile upward. Each commit corresponds to one crate reaching "compiles clean." Fix errors, commit, move to the next tier.

Section 05

The Commit-Speed Paradox

A commit every nine seconds is impossible if each commit includes a Rust compile. So either the timeline is fake — or the agent is not compiling between commits. The data points firmly at the second one.

Inter-commit gap distribution

Time between consecutive commits · n = 6,754 gaps

fast — pure write, no compile medium long — likely compile + test

What you'd expect

A sane per-commit cycle for a Rust project: write the code (~1 min), compile (3–10 min for a large crate graph), run the relevant tests (~30 s). That is 5–12 minutes per commit, minimum.

What actually happened

74% of commits land in under 30 seconds. More than 4,400 of the 6,754 gaps are 30 seconds or shorter. There is simply no compile happening inside that window.

The resolution: write and verify are decoupled

The agent does not gate each commit on compilation. It runs two loops at completely different speeds:

Fast inner loop
~9s median

Claude Code generates ~70 lines → git commit. No compilation. Just write and record.

⇄
Slow outer loop
hours

CI catches failures → sub-branches (ci-auto-fix, divergence-fix) repair them → merge back.

  • → Nine seconds is roughly the inference time for ~430 output tokens at ~150 tok/s — it is generation latency, not build latency.
  • → The diff sizes corroborate it: commits in the 0–5 second band average just 60–72 lines changed across 1–3 files — exactly what one focused generation step produces.
  • → The longer-gap commits (the red band) are where compile-and-test feedback actually lands — and those are the minority.

So the "impossible" speed is real and also mundane. The history is not fabricated. The agent simply treats compilation as an asynchronous concern handled by a separate loop — which is efficient, and also exactly why the open questions about correctness exist.

Section 07

Open Questions for Experts

The commit history proves the work happened and how fast. It does not prove the result is good. These four questions are where domain experts — in Rust, in systems security, in software supply chain — should be looking. Expand each for the detail.

› Question 01 Code Quality & Correctness

The PR reports a 99.8% test pass rate on Linux x64/glibc. That headline is strong — but the unexamined 0.2% is exactly where subtle correctness bugs hide, and a rewrite of this size has a lot of surface area.

The deeper question is idiomatic quality: is this real Rust, or is it Zig mechanically transliterated into Rust syntax? The two compile the same and behave very differently under maintenance.

The commit messages themselves show extensive automated diff-review passes — entries like "diff-review caught N bugs" recur throughout. That is encouraging, but it raises the obvious question: who reviews the reviewer? And phase-b2 commits explicitly mention "cache-hidden errors from T5" — errors that only surface later in the pipeline, after the commit that introduced them is long buried.

› Question 02 Memory Safety — The Unsafe Problem

This is the sharpest concern. The entire point of rewriting in Rust is memory safety — yet the phase-h commit messages reference "14,470 unsafe sites after r2" and "15,084 unsafe sites before r1." The tree is saturated with unsafe blocks.

The claude/unsafe-5k branch ran 27 times to chip away at them, but the net progress is hard to read from the outside. One representative commit — "phase-h: unsafe-wrap r4 — 672 sites / 23 strategies (−477 unsafe)" — shows roughly 470 sites removed per round.

At that rate, clearing 14,000+ remaining unsafe sites is dozens more passes of work that had not happened when the PR merged. A Rust codebase this dense with unsafe may be meaningfully less safe than a carefully hand-written Rust codebase — and arguably no safer than the Zig it replaced, until that long tail is actually retired.

› Question 03 Performance Claims

The PR claims benchmarks are "neutral or faster." But the claude/bench-until-green branch ran 19 rounds of optimization before merge — and the name says the quiet part out loud.

That is textbook selection bias: run the benchmarks, tune the code until they pass, then merge. It tells you the code can hit those numbers on those benchmarks — not that it is robustly fast across workloads the benchmark suite does not cover.

To be fair: the binary-size reduction of 3–8 MB is real and trivially verifiable by anyone — that one is not in question. But AI-tuned micro-optimizations have a known failure mode: they are brittle, tightly coupled to the exact benchmark shape, and prone to silent regression as the surrounding code changes.

› Question 04 Reproducibility & Auditability

One million lines merged into a production runtime with no human line-by-line code review is, simply, unprecedented. There is no prior playbook for auditing a change this large.

The history shows a ci-errors-to-tasks script: the agent auto-triages CI failures into its own task queue. Efficient — but it also means a human may never have seen the individual failures, only the aggregate green checkmark at the end.

Then there is supply-chain trust. If Claude Code carried a subtle bug in one translation pattern, that bug would not appear once — it would appear consistently across a million lines, everywhere the pattern was applied. Systematic errors are the hardest kind to catch by sampling.

And the PR was merged by a single person, Jarred Sumner. At this scale, it is a genuinely open question what the word "review" can even mean.

Appendix

Technical Appendix

› Proofs, raw objects, and how to reproduce

The git object model — how same-second commits work

A git commit is just an immutable object: a tree hash, parent hash(es), author line, committer line, and a message. Creating one is a hash computation — no compilation, no test run, nothing that touches the build system. There is nothing in git itself that prevents two commits from sharing a one-second timestamp. When an agent generates code and calls git commit back to back, sub-second and same-second gaps are the expected outcome, not an anomaly.

Author vs. committer timestamp proof

Every git commit carries two timestamps: author (when the change was written) and committer (when the commit object was created). A rebase, squash, or history rewrite changes the committer timestamp while preserving the author timestamp — opening a measurable gap between them. In PR #30412, 6,699 of 6,755 commits have an author/committer delta of under two seconds. That 99.2% is the fingerprint of history written live and never rewritten. The 56 outliers are consistent with ordinary merge mechanics.

Parent-chain topology

Of the 6,755 commits, 6,479 are linear (exactly one parent) and 276 are merge commits (two or more parents). The merge commits are precisely the points where the claude/* sub-agent branches fold their fixes back into the main port branch — the structural evidence for the two-loop architecture described above.

What git objects can and cannot prove

CAN be proven
  • ✓ Strict creation order of every commit (SHA-1 parent-preimage — cryptographically enforced, cannot be circumvented)
  • ✓ All batches are real, distinct tree snapshots — no empty commits, no duplicate-tree pointers
  • ✓ Claimed file and crate counts are accurate where countable ("36 crates" = 36 dirs, "96 crates" = 96 manifests — exact)
  • ✓ No post-hoc rebasing — author == committer timestamps everywhere in the sampled batches
  • ✓ Diffs are coherent and semantically reasoned, not templated transforms
CANNOT be proven
  • ✗ Whether the code was AI-generated or human-written — the object store records results, never authorship process
  • ✗ Whether diffs were generated live or pre-staged and replayed (byte-identical object graphs either way)
  • ✗ Actual wall-clock elapsed time — timestamps are author-controlled metadata
  • ✗ Whether GIT_AUTHOR_DATE was explicitly set — git does not record how a date was provided
  • ✗ Who designed the migration plan — the plan is expert-grade, but git cannot say if it came from an AI, a human, or a prior design document

Definitive proof of "autonomous AI authorship" would require out-of-band evidence: the agent's session transcript, CI build logs with independent timestamps, the harness execution records. Git is a content-addressed result store — it was never designed to prove process.
